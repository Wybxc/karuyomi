# 初版后的 Flutter 状态管理重构

## 目标与状态

状态：进行中。初版 Web 已交付；2026-11-12 按用户要求将逐页试点改为集中迁移，采用 Riverpod + riverpod_generator + flutter_hooks，并启用 riverpod_lint。不要在每批迁移之间重复等待整套人工平台矩阵。原生现场验证仍按用户要求停止，保留其待验状态。

Riverpod 负责跨页面共享的读取、派生状态与依赖装配；flutter_hooks 负责组件内重复的输入、焦点、动画与订阅生命周期。所有项目 provider 使用 `@riverpod` 生成声明，不同时维护手写等价 provider。两者都不改变业务权威和资源所有权。

原型阶段以快速迭代且不积累技术债为原则：直接调整当前架构和删除旧实现，削减重复机制与兼容负担。并发写入、身份隔离、未确认写入和资源关闭等真实复杂度必须完整处理，不以暂缓正确性要求换取代码减少。

## 集中交付范围

1. 固定现有书架、设置、阅读恢复和导航回归基线；补齐身份切换、共享订阅、重复挂载与前台刷新的请求计数。复用 repository / `BusinessStateClient`，不建立第二份业务存储。
2. 一并迁移书架列表、浏览列表的收藏标记、详情收藏状态、全局和作品设置的共享订阅。按已验证的服务地址与身份隔离 provider，移走 `AppShell` 的手工设置订阅装配，共用同一身份和作用域的设置命令控制器。保留显式刷新和写入命令；provider 的构建、失效与重试不得提交业务写。
3. 所有包含输入框、焦点、滚动、缩放、动画/标签控制器以及普通监听订阅的 Stateful Widget 采用 hooks，覆盖阅读器、章节详情、源迁移、跨源搜索、扩展管理、源设置/筛选、分类/批量编辑和诊断面板。纯 UI 组件使用 HookWidget；需要保留业务资源与逐帧状态的组件使用 StatefulHookWidget / StatefulHookConsumerWidget。Worker、Source、章节图片和阅读进度仍由既有持有者显式关闭并等待释放确认。
4. 固定 generator、annotation、hooks 和 lint 版本；生成物提交并接入一致性检查。`riverpod_lint` 随严格分析运行。生成器按需运行，不启动常驻 watch。
5. 集中执行静态分析、provider/组件/既有业务回归、完整格式检查和 Web 构建，并通过内置浏览器验收 Web 主流程。按可审阅里程碑提交、推送；原生现场验证和真机证据单独列为未执行，不将其伪称通过。

## 验收

- 格式化后生产手写 Dart 必须实质净减少；计入新增 provider，单列生成代码、测试与文档，说明删去了哪些重复实现。不得只叠加 provider 包装或压缩排版。
- Worker API + D1 仍是唯一业务权威。业务写继续走原提交路径，收到服务端确认才显示已保存；UUID、revision、epoch、幂等重试和未确认草稿的语义不变。
- 同身份重登保留未确认草稿；换身份或服务后不展示旧数据、不发送旧草稿；页面退订不提前释放在用资源或丢失待确认状态。
- 用实际前台刷新、书架/详情切换和重复挂载核对订阅、请求与重建次数；不为每个列表项增加请求，也不因 provider 失效而增加业务写。
- 集中通过生成一致性、riverpod_lint、严格静态分析、provider/组件回归和 Web 主流程。原生端共用代码通过平台无关回归；实际 iOS/Android 登录与读写仍保留待验，遵守已停止原生验证的要求。
