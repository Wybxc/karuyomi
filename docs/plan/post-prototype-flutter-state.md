# 初版后的 Flutter 状态管理重构

## 目标与状态

状态：未开始。初版按现有计划完成交付与验收后，开始采用 Riverpod + flutter_hooks 渐进重构客户端。初版继续使用现有 Flutter 状态管理和依赖注入，不把此次重构列为首发门槛。

Riverpod 负责跨页面共享的读取、派生状态与依赖装配；flutter_hooks 负责组件内重复的输入、焦点、动画与订阅生命周期。两者都不改变业务权威和资源所有权。

## 实施顺序

1. 固定与初版相同的跨端读写、阅读恢复和请求次数基线。先将书架的只读视图接入 Riverpod，复用现有 repository / `BusinessStateClient`；按已验证的服务地址和身份隔离，保留现有刷新入口及写入命令。
2. 试点通过后，逐步迁移作品收藏状态、已确认的全局/作品设置等跨页订阅。按功能拆分 `AppShell` 和 `CatalogController` 的订阅装配，避免引入第二份可写状态，也不在 provider 构建、失效或自动重试中触发业务写。
3. 在搜索、筛选和设置等小组件按需采用 flutter_hooks，消除重复的输入、焦点和动画控制器装配；Reader 的逐帧视口、手势、图片调度继续由原生局部状态持有。Worker、Source 与章节图片继续由现有持有者显式关闭并等待释放确认。

## 验收

- Worker API + D1 仍是唯一业务权威。业务写继续走原提交路径，收到服务端确认才显示已保存；UUID、revision、epoch、幂等重试和未确认草稿的语义不变。
- 同身份重登保留未确认草稿；换身份或服务后不展示旧数据、不发送旧草稿；页面退订不提前释放在用资源或丢失待确认状态。
- 用实际前台刷新、书架/详情切换和重复挂载核对订阅、请求与重建次数；不为每个列表项增加请求，也不因 provider 失效而增加业务写。
- 逐步通过静态分析、组件回归和 Web/iOS/Android 的书架读写、阅读续读与登录恢复分项，再推进下一批迁移。
