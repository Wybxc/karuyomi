# 跨语言协议方案：讨论待定

## 目标与状态

讨论如何减少 TypeScript Worker 与 Dart 之间重复维护消息模型，同时保留运行时不可信输入校验。状态：**讨论待定，尚未定案、未授权实施**。本文件不是实施任务，也不阻塞当前 P0；不得据此新增生成器、依赖或迁移现有协议。

## 当前事实

- TypeScript 维护源码的严格类型只在 TS 编译边界内生效，不能证明 Dart 与 Worker 接收的消息安全。
- 当前有共享协议版本/ABI 生成、TS/Zod 控制与帧校验，以及 Dart 手写模型/解析；尚无覆盖两端消息结构的单一 schema/IDL 生成体系。
- 版本、requestId/generation、Source Long 字符串、预算、取消与二进制正文仍是实际运行边界。静态类型或生成模型不能代替收到消息时的解析和限额。

## 尚待讨论

1. 确定要统一的范围：Dart↔TS 控制消息、Source DTO、错误、资源 handle 与生命周期；HTTP DATA/图片正文继续有界二进制传输，不经逐字节对象校验。
2. 比较成熟 schema/IDL 与双端生成方式。Protobuf + Protobuf-ES / protoc-gen-dart 是讨论候选，尚未选用；需验证 JS/Dart 工具链、浏览器可用性、生成类型与运行时验证职责。
3. 明确可空/可选、联合类型、未知字段/枚举、Long ID、版本错配与错误映射；原型阶段可直接更新当前协议，不以历史兼容拖累设计。
4. Pigeon 仅处理 Dart 与原生平台接口，不能替代 Dart 与 TS Worker 协议；必要时分别使用成熟工具，避免自制通用 IDL/序列化框架。

## 如后续授权实施，需满足的验收

- 一份明确的协议源生成两端类型/codec，生成结果可重复，并有漂移检查；删除被替代的重复维护模型。
- 边界仍检查消息结构、版本、requestId/generation、大小与状态；异常输入不能靠类型断言进入会话。
- 现有 DTO、二进制流控、取消、迟到结果与错误语义通过同输入回归，不因选用 codec 扩大正文缓冲或引入 Base64。
- 工具链、生成命令和源码/产物边界可维护；实施范围与结论经后续明确任务确定后，再更新为进行中。
