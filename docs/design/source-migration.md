# 用户确认的源迁移

源迁移把同一作品在两个 Source 下的书架状态关联起来，由用户选择目标作品并确认章节映射；Worker API + D1 仍是唯一业务权威。它不修改原 Source、URL 或章节身份，也不移动或删除原作品。实施状态与实际证据分别见[计划](../plan/source-migration.md)和[验证](../verification/source-migration.md)。

## 正式流程

书架与详情页提供迁移入口，在点击时捕获已确认的 `BusinessStateClient` 并显式传入页面和向导，不能在延迟创建页面时从当前账户重新取值。身份失效或客户端不一致会永久停用旧向导，即使之后恢复原客户端也须重新进入。详情已有章节时直接使用正式 `ChapterSequence`；书架进入时，用户选择读取原 Source 章节，或明确选择仅迁移收藏和分类。原 Source 不可用不自动降级，更不能声称已迁移章节标记。

目标来自当前默认仓库中账户已确认安装、启用且精确构建可用的 Source。打开、搜索分页及读取目标详情/章节复用正式 `CatalogController`、运行时、统一中继和 Source preferences 路径；迁移搜索结果独立展示，不覆盖普通浏览分页。取得目标后，只读获取原/目标作品、完整已读与书签列表，以及分类目录；任一分页失败或读取期间 revision 改变都拒绝该预览，不能把未读取状态当作未读。

预览显示目标身份、分类选项、章节映射和目标已有状态，再经独立确认提交。目标会加入书架；原作品保留，移出原作品由用户另行决定。成功只在服务端确认后呈现，不自动导航；结果按实际新增的已读/书签数量显示，不把请求条目数当作新增数量。

## 章节身份与匹配

漫画身份继续使用 `SHA-256(JSON[packageName, sourceId, mangaUrl])`。章节映射传 `ChapterSequence.key`：唯一 URL 对应完整稳定身份；重复 URL 保留原快照与索引身份，不按标题或章节号去重。章节原始顺序、零章、小数章和缺少章节号均须保留。

建议要求归一化标题非空且相同、双方有效章节号相同，以及归一化扫描组相同；双方均未提供扫描组时，不能把缺省值说成额外证据。仅去首尾空白、统一空白和大小写，不删除标点或猜测章节号。负数、缺失或非有限章节号视为未知，零和小数保留。双方必须是稳定章节身份、完整签名唯一，且同一目标不能被多个原章节认领，才产生可预选建议。缺少有效章节号、仅标题/章节号相近、重复 URL 或其它歧义只提供候选，须用户手动确认；未映射项不自动标已读。

所有章节均可逐页查看，手动选择可访问完整目标章节列表，不限制在建议候选中。同一次提交源键和目标键均唯一，每组至少选择复制已读或书签；最多 256 组。超过预算必须明确减少选择，不静默截断，也不暗中拆成存在部分成功的多次写入；后续剩余项可以另行预览并确认。

## 协议与原子写入

沿用 `protocol/karuyomi/v1/business.proto` 和既有 `POST /api/state/mutations`，不新增迁移表、专用写路由或客户端业务数据库：

| 协议字段                                              | 含义                                                     |
| ----------------------------------------------------- | -------------------------------------------------------- |
| `StateMutation.mangaKey / expectedRevision`           | 目标作品及预览的目标 CAS                                 |
| `MigrateFrom.sourceMangaKey / expectedSourceRevision` | 原作品及预览的原作品 CAS                                 |
| `MigrateFrom.expectedCatalogRevision`                 | 预览分类目录 CAS                                         |
| `MigrateFrom.targetMetadata`                          | 用户确认的正式目标 Source DTO 快照，身份必须与目标键一致 |
| `MigrateFrom.copyCategories`                          | 是否合并原作品分类                                       |
| `MigrateFrom.chapters`                                | 一对一的源/目标章节键与 `copyRead / copyBookmark`        |
| `StateMutationResponse.migration`                     | 实际新增已读数及书签数                                   |

沿用标准 ProtoJSON、生成 TS/Dart codec 与双端运行时语义校验。整个请求仍受 128KiB UTF-8 预算限制；映射数量、标记、身份、版本和 revision 同时校验。源与目标必须不同，原作品须已有 metadata；不要求原作品此刻仍收藏。

服务端先读取预览对应的资料，再以原作品、目标作品、分类目录三项 CAS 在同一个 D1 `batch` 的幂等获胜条件中重新检查。原 mutation UUID、请求 hash 和独立 `attempt_nonce` 约束整批影响；只有本次成功获胜才能写目标、分类、已读和书签。竞争或任一 SQL 失败均不产生部分迁移；同 UUID/同 body 重试返回原确认，异 body 不能复用 UUID。

章节写入使用有界 `json_each` 数组，256 组仍为固定八条事务语句，不为每章生成 SQL 或建立 staging 表。源作品和其章节记录全程不写。目标行为如下：

- 目标设置为收藏；仅缺少 metadata 时填入目标快照，已有 metadata、自定义封面、resume 及其它业务状态保留。
- 选中分类与目标分类取并集，不替换分类目录或覆盖目标已有成员。
- 只有源章节已确认 `completed=true` 且目标完全没有 progress 行，才新增 `completed=true, epoch=1` 的记录；不携带原 current/furthest、页键、manifest 或锚点。目标已有任意 progress 整行保留，包括明确未读、epoch 和位置。
- 只有源存在书签且目标缺少书签时新增；不删除目标书签。不把未读、缺记录或旧页位猜测成已读。

新增已读使用 epoch 1，使另一端按目标旧 epoch 0 准备的进度草稿被正常拒绝；它不能证明旧阅读位置可跨源使用。源章节页面位置、原阅读顺序、封面、resume 与 epoch 均不跨源复制。

## 待确认、冲突与生命周期

预览对象冻结源/目标/目录资料和三个 CAS。提交同步占用两个作品，按固定顺序复用既有分类与作品队列；不在真正写入前偷偷重读并改成新 CAS。未确认迁移保留在同一业务客户端的会话内存中，保护源、目标与分类编辑，防止另一操作覆盖原请求；无持久 outbox，也不承诺关闭应用后恢复。

ACK 未知时只能显式重试原 UUID、完整 body 与三个 CAS；只读刷新、重新进入页面不隐式 POST，重新创建 repository 包装器不改变 pending。服务端已明确拒绝后，用户显式放弃已拒绝草稿，再重新预览并确认；未知请求不能直接丢弃并另发同一操作。确认旧幂等结果时沿既有只读重取规则核对当前权威状态，不用旧 ACK 回退其它客户端已确认的新目标。

每次异步读取前后以及排队后的真正 POST 前均检查页面/身份是否仍有效。页面关闭或身份变化后不继续后续 GET、发出新 POST 或导航；已经发出的写由业务客户端处理 ACK 和必要的只读重取，旧页面不能把迟到结果用于继续新动作。切换 Source 会使旧详情运行上下文失效，迁移流程绑定自己的身份与业务客户端，不依赖原 Source generation 长期存活。

## 验收边界

合同、真实 workerd/D1、Dart 数据层、正式组件、真实 Source、独立客户端、生产 Access 和 Native/真机分别验收。模拟 Source 或测试供应器只证明相应工程路径；编译成功的 AOT 仍保持 `compiled_unverified/runtimeReady=false`。当前实际范围以[验证记录](../verification/source-migration.md)为准。
