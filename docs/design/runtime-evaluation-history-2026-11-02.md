# 运行时选型历史（截至 2026-11-02）

本文保留切换 TeaVM release9 之前的研究记录，可正常补充、更正，不再冻结。历史“默认 CheerpJ”“仍待全量/性能验收”等描述只反映当时研究，不作为实施要求。当前 Flutter + TeaVM 方案见[主设计](./mihon-web-design.md)，实施状态见[计划目录](../plan/README.md)。

当前交付以 Static Assets 为所有客户端扩展的最终权威来源，只发布每扩展最新 build；客户端或 Service Worker 按 index/catalog 管理版本与缓存，不再要求扩展 Release 发布，已有扩展和索引 Release 已按用户要求删除；通用资源由 Web Static Assets / Native 内置提供；Worker 不代理 AOT 正文。下文早期私有 R2/Access 产物交付提案已取消，历史性能也不构成公开下载或产品 Source 验收证据。

### 已核对的预加载性能基线（2026-11-02）

已读取参考聊天最新两轮结论、`STARTUP-REPORT.md`、`EXTENSION-STARTUP-REPORT.md` 和原始样本，复算下表中位数；本次没有重新运行浏览器性能测试。环境为 CheerpJ 4.3 / Java 17、桌面浏览器 WebWorker、本机 Miniflare/workerd；插件请求使用配置的 HTTP CONNECT 出口，尚未加入产品的 Access 鉴权链。

宿主 A/B 从创建 Worker 计时至 `Host.init()` 响应，不含扩展加载或业务调用。每条件 5 次，另有不计入统计的预热样本；串行新建 JVM，开关按 AB/BA 交替，共 20/20 通过。

| 资源条件           | 预加载关 | 预加载开 | 中位耗时减少 |
| ------------------ | -------: | -------: | -----------: |
| 已有浏览器缓存     | 4.429 秒 | 2.184 秒 |        50.7% |
| 运行时数据重新下载 | 6.753 秒 | 4.043 秒 |        40.1% |

本组开启预加载且已有缓存时，`cheerpjInit()` 调用中位数仅 0.019 秒，库与宿主阶段为 2.146 秒；不能把单个初始化 API 返回当作扩展宿主已就绪。所有开启样本在宿主就绪前完成预加载，默认开启后的 ABI/JS/DOM/Zstd 等 5 项运行时探针通过。

累计值均由单次完整链路独立计时，不能将不同阶段或不同实验的中位数相加。已有缓存时，三个插件加载阶段的中位数仅 60–179 毫秒；当前证据更支持优先保证资源缓存和宿主预热，而非预先加载全部插件或引入更多 JVM。首次业务调用包含上游请求和解析，不能将它全部算作 JVM 成本。

**适用边界：**

- “已有缓存”仍然每轮新建 JVM，证明复访时不必固定等待此前讨论的 7–12 秒；它不是同一存活 JVM 的热调用。
- 宿主 A/B 的“重新下载”只绕过运行时 CDN 的 fetch HTTP 缓存；插件组还绕过本地宿主和扩展 JAR 的 fetch HTTP 缓存。两组条件不同，loader、模块、编译和持久文件缓存仍可能复用，都不代表全新浏览器完全冷启动。
- 本地 JAR 不含公网传输延迟；生产 Access 重验证、Cloudflare 出口、移动设备和网络状况均可能改变结果。Comic Fury 重新读取组范围 5.547–11.812 秒，仍需等待状态和错误恢复。
- 本轮只到热门列表，未测详情/章节/页面解析、图片请求/解密/解码及首图显示，也未重跑 447 个 Source。每条件 n=5，报告 P90 等于该组最大值，不作为稳定尾延迟或全平台性能承诺。

### 产品启动策略与后续验收

上述约 2 秒宿主、约 3 秒首个列表是较早预加载原型的参考量级；下节 b-jvm 对照采用了更新的公共宿主，不能将两个批次直接拼成运行时排名。产品继续采用纯 Workers 和浏览器共享 JVM，默认保留预加载；首屏、Access 验证和必要的数据同步分开调度，登录确认后的前台预热可以覆盖用户浏览书架的一部分时间，但不能直接从样本推算省去多少点击等待。

设计预算仍为待测目标：本地书架热开 <1s；缓存页操作响应 <100ms；首屏不等待 JVM；一次同步合并多条进度。同一次前台使用期间不因返回书架、切换页面/源或短暂空闲销毁 JVM；优先释放临时图片和不必要对象，长期无活动或资源压力下才回收运行时。关闭或被系统回收后按新会话初始化，不依赖跨关闭周期常驻。

P0 补测“打开应用至首张漫画可见”的完整链路，单列 Access 探测/交互登录、宿主就绪、扩展加载、首个有效列表、章节页面列表、首图可见和内存峰值；交互登录等待不混入 JVM 指标。覆盖资源缓存命中、重新读取、全新浏览器和同 JVM 复用，并在 Android Chrome、iOS Safari/PWA 与线上 Workers 出口验证；记录失败率与实测分布后再确定移动端预算。原型测试页与结果接口保留在开发环境，不成为公开产品后端。

原型每 500ms 一次的空轮询每小时约 7,200 请求，应在产品化时消除。预加载收益不会替代图片链路、回调兼容性与访问控制验收。

### b-jvm 替换评估（2026-11-02）

**决定：暂不将首版默认运行时改为 b-jvm。** 对于目前“个人使用、保留原版扩展、兼容多个源”的目标，已测的小幅启动收益尚不足以抵消大响应耗时、资源交付和运行时维护成本。若将源码可控、自行托管运行时作为首要目标，b-jvm 的价值会明显提高；它作为后续候选保留。

证据来自聊天[实现并对比 b-jvm 原型](codex://threads/01a199bf-5186-77d3-b806-39ad3ee513ad)及其 `outputs/b-jvm-prototype/` 中的 `PERFORMANCE.md`、`COMPATIBILITY.md`、`LARGE-RESPONSE-ANALYSIS.md`、`GSON-PERFORMANCE.md`、机器可读汇总与宿主/桥接代码。本次核对数据和实现，没有重新跑浏览器基准。b-jvm 是固定提交 `3fd56c74656602eb32efefca46f51f074bef6bca` 加项目补丁、Java 23.0.1 加补充资源；CheerpJ 是 4.3 / Java 17，已启用预加载。结论限于这些构建。

**同批启动收益。** 同一桌面浏览器、本机 workerd/代理、相同公共宿主和原版插件字节码，新建 Worker 至首次有效热门列表，已有浏览器缓存：

| Source       |    b-jvm |  CheerpJ |    b-jvm 节省时间 |
| ------------ | -------: | -------: | ----------------: |
| MangaDex     | 1.661 秒 | 1.787 秒 |  0.126 秒（7.1%） |
| Webtoons.com | 1.956 秒 | 2.207 秒 | 0.251 秒（11.4%） |
| Comic Fury   | 3.043 秒 | 3.651 秒 | 0.608 秒（16.7%） |

每条件 5 次尝试，CheerpJ/MangaDex 因一次代理断连只有 4 次成功计入耗时，其余各 5 次；分布有重叠，不作显著性结论。宿主就绪中位数约为 b-jvm 0.67–0.68 秒、CheerpJ 1.00–1.03 秒；首个列表的收益包含网络波动，不能全归于 JVM。重新读取组中 b-jvm 的文件走 localhost，CheerpJ 运行时走供应商 CDN；其 2–3 倍差距不能作为公网完全冷启动优势。

**兼容性已有较强基础，但仍有实际缺口。** 两者均通过 138/138 插件加载、1,038/1,038 Source 的元数据与设置，返回结构一致；77 个代表 Source 五项业务全通过为 b-jvm 66/77、CheerpJ 68/77。该差值混合了站点、网络、缓存与超时，不能解释为只有两个 JVM 缺陷，也不代表全部 1,038 个 Source 的业务和图片通过。Yaoi.me 的章节调用两次复现 b-jvm 缺少 `UnixFileDispatcherImpl.read0`，涉及加密初始化读取策略文件；CheerpJ 通过。

**大响应会影响整个使用过程。** Coomer、Pawchive 延长等待后都能完成业务，但 b-jvm 热门/搜索约 33–49 秒，对照 CheerpJ 约 4–7 秒；另一个两边都通过的 JJCOS 热门/搜索约为 20/26 秒，对照约 3/3 秒。它们是诊断观测而非同缓存多轮纯 JVM 跑分；不过无网络分项测试也复现计算差距：相同 Java 内生成输入、相同 Gson，4 MiB 长字符串解析为 248.7/25.1 ms，约 3,576 万字符为 2,308.6/169.2 ms。256→512 MiB 堆对后一项仅改善约 0.44%，不支持把加堆容量当作主要解法。

固定 b-jvm 提交的 `attempt_jit()` 提前返回，Java 热点仍解释执行；原型 JSON/Base64 桥、字符串复制与文件 mailbox 又增加处理量。二进制桥有望减少其中一部分开销，但尚无优化后的端到端证据；2.31 秒的合成长字符串解析也不足以解释约 41 秒的真实业务，不能承诺移除 Base64 后与 CheerpJ 等速。[固定版本源码](https://github.com/anematode/b-jvm/blob/3fd56c74656602eb32efefca46f51f074bef6bca/vm/interpreter2.c)。

**资源与维护成本。** 当前 b-jvm/JDK 资源共 142.29 MiB，另有公共宿主依赖 35.98 MiB；这些是磁盘未传输压缩大小，不是实际网络下载量或峰值内存。实现会将 JDK 分片在浏览器拼接，并写入 WASM 文件系统，配置 Java heap 256 MiB，尚缺手机峰值内存与能耗证据。不能只用 0.90 MiB 的 WASM 判断它轻量。现有运行时补丁涉及文件、Unicode、类元数据、Unsafe、异常与调度等 17 个上游文件；基础 JS native 桥仍用每 2 ms 扫描一次的内存文件 mailbox。补丁已经做出，迁移时无需重做，但后续升级、诊断和语义回归需要维护。

b-jvm 的开源代码使运行时修复、自建资源交付和按需裁剪成为可控选项；引擎使用 [MIT 许可](https://github.com/anematode/b-jvm/blob/3fd56c74656602eb32efefca46f51f074bef6bca/LICENSE)，JDK 和依赖仍各自保留声明。它不需要修改扩展字节码，也能沿用当前一个 hostname、前端公开/API Access 鉴权的结构。仅为了首版启动速度，现有证据还不值得承担这些额外工作。

**下一步优先级及切换条件。**

1. 先执行第 5 节 P0-A 公共宿主改进；同批 CheerpJ 宿主约 1 秒作为对照参考，不把相对旧批次的全部变化单独归因于它。先用旧桥独立验证宿主，再重采集预加载清单。
2. 执行第 5 节 P0-B 二进制桥，先交付 CheerpJ，保留相同协议供 b-jvm 后续适配。固定响应重放分别计时桥接、插件解析、图片处理和首图；不得通过改扩展、跳过拦截器来取得速度。
3. b-jvm 在考虑替换前，修复并回归已知 `read0` 缺口，验证真实回调/文件缓存及长时间会话；对拟支持源保持相同成功率和操作期限，消除相对 CheerpJ 的数十秒级回退。不能仅放宽超时来通过性能门槛。
4. 在同等资源交付、干净浏览器、线上 Access 和目标手机上测首图、后续切章、长图处理、真实下载字节、峰值内存及耗电。只有真实使用收益足以补偿资源与维护成本，或用户明确优先源码可控/自托管时，再调整默认运行时。

首版仅保留可替换的 `SourceRuntime` 边界。开发环境可以选择候选后端；产品不同时加载两套 JVM，也不在失败后自动用另一运行时重放请求，以免引入双份初始化、状态同步及有副作用操作的重复执行。此评估不扩大已暂缓的功能范围。

### TeaVM 替换评估（2026-11-02）

**更新判断：建议将 TeaVM 作为目标运行时推进产品集成；当前发布设计仍暂留 CheerpJ 基线，待最终候选验收后切换。** 本批原版扩展的编译加载、脚本桥、真实 HTTP 缓存和图片处理已有充分进展，第五候选全量已完成，普通 Java 文件持久化也已定向修复。剩余优先事项收敛为包含全部修复的候选同版验收，以及完整兼容层下的手机/PWA 性能。完成这些门槛后可切换，不以补齐整个 JVM/Android API 为目标。本项目接受开发机/CI 产物处理，按包 AOT 的架构成本仍可接受。

同一筛选样本中的历史 CheerpJ 为 430 个读链、425 个五项均非空、2160 项业务通过。第五候选的业务观测已接近该历史水平，足以支持产品集成验证；两者不是同时、同输入的全量对照，不能将 424 与 425 的差值解释为只剩一个引擎缺陷，也不能把第四候选 1949→第五候选 2167 的全部变化归因于代码修复。

**需要改变的比较方法。** 旧失败集合 13 包/48 Source/240 项固定输入配对中，两边业务状态相同，但发现 JSON 字段、请求顺序/数量差异，后续因果检查给出了不同解释：

- Coomer 少发请求来自 TeaVM 正确命中缓存；旧 CheerpJ 宿主未执行内部 CacheInterceptor。强制缓存读取 miss 的诊断路径恢复相同请求数且输出不变。不能为了匹配旧宿主关闭正确缓存。
- XCOMIC 在同一个 CheerpJ 中改变响应完成时序也会请求换序；并发没有唯一总顺序。比较合法依赖关系、请求内容、结果和副作用，并保留实际顺序，不能把任意排序后的结果当作全部竞争路径已等价。
- CosplayTele/IMHentai 的输出字段虽然相同，文件状态却不同。必须把跨 Worker 持久状态纳入验收，不能只检查 count、序列化字段或请求集合。

旧严格配对的失败记录不追改为通过。第三/第四候选失败并集已扩至 16 包/93 Source/465 项计划，还需纳入后续候选；重新采集的 fixture 可以验证当前差异，不能证明未保留响应正文的历史失败原因。两边同样报错也不是业务成功。

**普通 Java 文件持久化已定向修复，整批集成待验收。** 旧版中，未修改的 CosplayTele/IMHentai 分别写出 729/11 字节筛选文件，新 TeaVM Worker 丢失而 CheerpJ 保留；业务输出相同并未暴露这一状态缺陷。独立 `persistent-files-candidate2` 已通过 51 项 JVM 对照和 70 项浏览器检查（两组有覆盖重合，不能简单相加）；8 Worker/40 项原插件业务无字段、状态或异常差异且无 fixture miss，新 Worker 保留文件和修改时间，筛选请求恢复为 1→0、5→0，与 CheerpJ 一致。修复前失败审计保留，修复后另有通过审计。

实现通过 TeaVM 虚拟文件系统接口接入 IndexedDB，事务提交后恢复 Java fiber；支持节点/句柄、原子 rename 与替换，宿主 init/load/select 改为可等待入口。定向检查覆盖独立文件并发写入、并发追加、事务中断和 Worker 异常终止后的句柄回收；Worker 生命周期使用 Web Locks，未采用整棵文件树退出快照。该修复直接支持按需回收 Worker 和 PWA 重开，但第六候选同版回归尚未完成。

产品接入时还需在目标浏览器验证安全上下文下 IndexedDB/Web Locks 可用性、多标签页与身份/扩展命名空间、启动恢复成本。当前每个文件正文存为单个数据库值，大文件内存和吞吐未测；宿主文件 I/O 必须计入性能，不能在测量开始前隐去。只在浏览器内持久化扩展运行文件，不增加章节下载、本地漫画或云端文件同步功能。

**部署可以保持纯 Workers，扩展分发则需要改变。** TeaVM 将字节码提前编译为浏览器程序，运行时不再具备通用 JVM 那样装载任意新 JAR 的能力；反射、资源和类加载需要构建期配置。[TeaVM 官方概述](https://teavm.org/docs/intro/overview.html)。当前原型保持原扩展 JAR 哈希不变，适配通用宿主、依赖与编译器映射；这符合不修改网站解析业务的约束，但不代表无需维护兼容层。

若后续采用 TeaVM，建议采用以下产物和运行方式，先验证再替换主架构：

1. 开发机/CI 执行“原版 JAR（或 APK 转换）→ 按包 AOT → 业务与图片检查 → 发布清单和 bundle”。新增或更新扩展只构建对应产物；公共宿主/编译器变更则使相关构建缓存失效并触发回归。无需为每个扩展重建前端，也不需要常驻构建服务器或线上 JVM。
2. 清单记录包/版本、原始产物哈希、转换版本、TeaVM/宿主版本、产物哈希、ABI 和验证范围。安装、升级、回滚都选择已构建版本；没有匹配产物时显示“待构建/不支持”，不能承诺上传任意 JAR 后立即可用。保证可重新构建和业务一致性；原型重建的 JS 哈希不同，不能声称已有字节级可复现构建。
3. 原型每包独立编译，原因包括扩展中的同名 `keiyoushi.source.Generated` 类；当前 JS Worker 还使用全局入口，不能直接把多个 bundle 顺序装进现有共享 JVM 的位置。先采用按需启动、数量受限、可复用和回收的浏览器 Worker 执行槽，验证跨源搜索调度及取消；这是产物与内存管理选择，不增加第二 hostname 或恶意扩展沙箱要求。设置、Cookie、作品和阅读状态由宿主统一管理，不能仅存于可回收运行实例。
4. **当时的交付提案（已取消）：** 扩展在浏览器执行，Worker 提供 API/网络桥，并以私有 R2 和鉴权缓存重验证交付 bundle。当前采用全客户端 Static Assets 最新扩展交付，不再要求扩展 Release 发布，已有扩展和索引 Release 已按用户要求删除，Access 仅继续保护个人数据和 Source 网络控制；不保留这条旧产物代理路径。资源获取、CSP 和启动失败恢复仍需按当前链路验证。

**新版体积和构建成本已有可核对数据。** 从第五候选 `build-matrix-release5.json` 复算：77 个 JS bundle 共 285.88 MiB，中位 3.36 MiB，范围 2.03–42.24 MiB；最大为含完整 ICU 数据的 ProjectSuki，其余最大约 4.02 MiB。该批本机构建每包耗时中位 25.13 秒，包含并发构建环境影响，不是首次无依赖缓存的 CI 耗时。以上均为未压缩产物大小，不是网络流量、峰值内存或必须一次下载的总量。

按包编译和按需获取仍适合个人常用源集合，但不应把全仓产物加入 PWA 首次预缓存。各包重复包含运行库，需限制同时驻留，记录实际传输量、解析时间和峰值内存；重包另验证资源交付或有依据的裁剪，不能假定所有扩展都维持百毫秒启动。当前 HTTP Cache 存储桥仍有目录扫描，异常终止后的同键写锁租约最长保留 5 分钟；大目录性能、启动恢复和异常终止恢复时间都应单列，正常关闭/取消立即释放。WasmGC 可另做实验，不作为当前迁移的前提；其模块加载器加载的是已编译 Wasm，不恢复动态 JAR 装载。[官方模块加载说明](https://www.teavm.org/docs/wasm-gc-backend/loader.html)。

公共宿主改进和二进制网络桥继续保留。浏览器 HTTP 传输、OkHttp 语义、DTO、Access、协议和固定响应测试可复用；CheerpJ 预加载与 Java 字节接口是其专用适配，不能直接视为 TeaVM 已实现。TeaVM 初始原型仍使用 JSON 文本桥，AOT 不会自动消除 body 的 Base64 往返；其二进制适配同样要验证字节复制、背压和取消。若 TeaVM 在进入对应实现阶段前通过门槛，再选择一个产品默认后端并调整 P0，避免同时维护两套完整产品路径。

当前结论不把 TeaVM 迁移变成 P0 的阻塞条件，也不增加暂缓功能。对个人常用源完成验证后可以采用 TeaVM，无须以完整复刻 Android/JVM 为目标；兼容性未覆盖的源明确标注限制。CheerpJ 保留为开发对照和版本回退选择，不做用户端自动双引擎重试。

新增资产应优先围绕通用 DTO、原版扩展哈希、固定响应、Access 和二进制协议构建，避免将更多产品逻辑绑定到 CheerpJ 专用 API。TeaVM 定向文件修复、最终版完整阅读和性能通过后，再同步切换架构图、运行实例管理和 P0 适配目标；本次评估没有宣布已经迁移。
